# Architecture and measurement contracts

The FastAPI application owns HTTP, React assets, immutable profile documents, history, baselines, and event delivery. SQLite uses WAL and explicit transactions (`user_version` migrations). Artifact paths are resolved beneath an individual run; exports never traverse symlinks. State lives under `data/`, shared with the controller. `/api/events` notifies the browser that state changed; a new connection starts after the latest event, and a reconnect resumes from `Last-Event-ID`.

The application has **no Docker socket**. The separate trusted runner uses its local Docker daemon only for Bench Studio workers and verification containers. The model router and AI Runtime may run on another LAN host. New jobs select one healthy, currently advertised model by its router service ID; the runner waits for router idleness, pins the canonical model and its discovery metadata, and revalidates model identity while queued and running. Discovery uses the router's capabilities document; the runner holds its event stream (see the [LLM Router contract and conformance map](llm-router-contract.md)). Historical multi-target jobs remain readable. Runtime load detection is observational, not an exclusive host reservation.

A submission idempotency key prevents duplicate queue entries, including a browser retry after a discovery outage. Queued jobs survive restarts. Worker ownership is committed before Docker start; an existing worker is inspected and reattached, never blindly replayed. Missing workers are interrupted. A controller restart interrupts a Harbor harness and stops its labelled sandboxes because replaying an agent conversation would invalidate repeatability. Cancellation targets only that run's process group and Docker labels.

Speed workers call pinned BetterBench through `invoke.py`. The upstream tree is unchanged. The explicit adapter forwards supported extra request parameters and preserves the engine's workloads, timing, weighting, warmups, and calculations. Prefill always uses temperature zero. Reports retain the actual prompt depths and measured metrics.

Quality workers generate source as data, then exit. Separate verifier containers run EvalPlus / TypeScript compilation and MultiPL-E tests with `--network none`, no GPU, no Docker socket, no credentials, a read-only root, CPU/memory/PID limits, and only that target's output directory mounted. The EvalPlus adapter supplies the selected original problem records to the unmodified evaluator, retaining both base and extended tests. Full Python has 164 eligible tasks and full TypeScript 159; combined full has 323.

Repository tasks use a trusted Harbor/Terminus 2 harness in the runner and isolated Docker task environments. Only the harness reaches the router. `RouterTerminus2` replaces the upstream non-streaming transport with a strict SSE collector; prompts, parsing, turn accounting and terminal actions remain the pinned Terminus 2 implementation. It requires real token usage and a clean stream end, and makes no automatic transport retries. Task containers use `network_mode: none`, only SETUID/SETGID capabilities (needed by older npm to drop privileges), no GPU or host credentials, and no Docker socket. Dependencies and native libraries are prepared before measurement. Verification preserves the official required-test sets. Task images and input manifests are pinned; TypeScript verifier wall time starts at a recorded fixed noon to eliminate upstream calendar tests' time-of-day dependency. Monotonic time remains real. See the task preparation guide.

Each run saves model identity, quantization, context/reserve, runtime revision, router-supplied service identity, requested sampling, profile fingerprint, engine versions, task-manifest hash, and local execution image IDs. Backend engine arguments and defaults are recorded as unavailable when remote APIs do not expose them; they are not inferred from local Docker or fixed backend ports. Raw request artifacts retain actual token counts and finish reasons. Invalid streams or absent measurements fail the run rather than estimating a score. A model/configuration change blocks queued work or invalidates active work. A service the configuration stops is offline, not changed: queued work waits for it and active work fails without being invalid.

Scores remain separate: decode throughput, prefill throughput, coding pass rate, repository resolved rate. Comparisons reject different workloads, sizes, modes, engine versions or task manifests. Changed model, context, runtime, hardware, image, and generation settings are displayed. Percentage correctness differences are percentage points; throughput differences are relative percentages. Small smoke samples do not establish statistically significant improvements.

Coding sessions use the versioned `StudioSessionAgent` Harbor interface and the same strict streaming transport. A controller-owned protocol enforces read-only planning, durable approval, bounded implementation and independent verification. Waiting reviews release the inference scheduler; resumption rechecks runtime identity and idle state. The child watches its controller's lifetime and cancels in-flight work after controller loss. No work is replayed. SQLite migration 2 adds review records without changing historical runs or baseline slots.

Session environments contain only prepared application sources and dependencies. Candidate sources are size-bounded snapshots; deletions are retained, and protected build/regression inputs must match the pinned base. Fresh offline verifier containers receive trusted acceptance checks through a separate read-only mount staged in the host-shared data directory. Reference solutions and private acceptance checks are absent from agent environments. Commit-ready artifacts include the independently verified patch, file list, checks and proposed commit message.

Vision checks use pinned screenshots and actual image requests. Visual design adds offline rendering, screenshot critique, objective interaction/layout evidence and sandboxed prototype previews. Human design approval is distinct from unattended acceptance. Suite eligibility requires matching offline validation; each suite can be checked independently. Model smoke tests are optional and do not determine eligibility.

Compose also builds the pinned session environment. The `SessionSetup` controller waits for an explicit eligibility request; deployment does not start checks. Offline eligibility checking holds the shared execution lock while health heartbeats continue, labels all preparation containers for scoped cleanup, and preserves failures instead of retrying indefinitely. Optional model checks are submitted idempotently through the same launch validation and durable queue as user jobs. Compatible receipts skip repeated eligibility checks; changed execution images invalidate suite availability until revalidation.

Session outcomes retain active and excluded phase timings, failed-attempt consumption, actual request usage, compaction evidence and review history. Time deltas use matching successful attempts only and are withheld when review feedback differs. A fixture, execution image, protocol, task budget, tier, task selection, repetition count or review-mode change creates a different baseline slot. Existing throughput/function baseline keys remain unchanged.
