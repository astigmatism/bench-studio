# Update and recovery

Exactly one long-lived Compose service (`reports`) carries Service Portal's update and lifecycle labels. The updater image is built in advance and contains Git, Docker CLI, Compose, Python/SQLite. Portal mounts the checkout at its original absolute path and supplies Docker's supplementary group. UID/GID defaults to 1000:1000. No SSH keys or GitHub token are needed to fetch the public repository.

The Update action refuses dirty source, detached/wrong branches, unexpected origin/upstream, divergent/unpublished local history, an invalid `PROJECT_DIR` or data mount, or an active benchmark. `PROJECT_DIR` must be the absolute path of the checkout mounted into the updater. Both reports and runner must bind its `data/` directory; the runner also sees that directory at its host path for worker mounts. An atomic `.execution.lock` shared with the scheduler prevents a launch racing Update. `.maintenance` blocks new launches. A queued job remains in SQLite after an Update of a running service and is blocked for review if its saved application revision changed.

Stop writes `.maintenance` with a durable snapshot while holding the database write transaction. Portal passes the Stop request time, so a run that finished before the helper started is still captured if it finished after the request. It then stops `reports` and `runner`, removes this installation's labelled transient containers, deactivates any eligibility request, and deletes the captured runs' records, run directories, and exports. Partial request-scoped eligibility preparation files are removed; completed preparation receipts and evidence remain. Small `deleted_runs` tombstones prevent interrupted cleanup from reimporting legacy manifests. Completed and older terminal history remains. A cleanup error makes Stop fail and leaves the guard in place. Start retries that cleanup, starts both services with `--no-build`, waits for health, and only then removes the guard. Update can also finish pending Stop cleanup before fetching and rebuilding; a failed Update from a stopped service leaves its Stop guard in place.

Update sequence: validate checkout/tools/Compose data mounts; lock and check active jobs and pending reviews; fetch and fast-forward; validate the fetched Compose data mounts; back up SQLite with the live backup API and save previous image identities; build all six images (including the session environment); reconcile `reports` and `runner` with a 150-second health wait. A failed build restores previous image tags before releasing maintenance. Failed restoration or failed deployment health keeps maintenance active for recovery. Errors remain nonzero for Portal. The script does not use global prune, remove volumes, or bring down the application stack.

After a healthy restart, compatible prepared suites remain available. If fixtures need preparation, select **Check eligibility** in Bench Studio; eligibility checks use no model requests. Optional model smoke failures never disable prepared suites. Updates and restarts never initiate preparation or qualification; the retired `SESSION_AUTO_SETUP` setting is ignored. Existing compatible receipts are reused. Portal success certifies application/controller health, not model task success. If an explicitly started eligibility check blocks an update, select **Stop eligibility check** and wait for its cleanup to finish, then retry the Portal action. This stops eligibility-owned preparation and smoke runs while retaining evidence; ordinary user benchmarks still require their own Stop action. Controller interruption requires selecting **Check eligibility** again. Failed live model qualifications can also be retried with **Run again**. See [suite eligibility](coding-sessions.md).

Backups are under `data/backups/TIMESTAMP/`, containing `studio.sqlite3` and `deployment.json`. Raw `data/runs/`, configuration, and downloaded task environments remain in place. `data/`, `.env`, and downloaded caches are ignored by Git and are not copied into replacement images. Dataset preparation verifies committed manifests without rewriting them, keeping a clean source checkout for Portal updates. Keep an external backup of `data/` for disk failure recovery.

## Roll back after a failed deployment

1. Confirm no benchmark is active. Stop only this application's services with `docker compose stop reports runner`.
2. Preserve the current database and its `-wal`/`-shm` files in a new recovery directory. Read `deployment.json` to identify the previous source revision and image IDs.
3. Restore the backup `studio.sqlite3` into `data/`; remove stale `studio.sqlite3-wal` and `studio.sqlite3-shm` only after both services have stopped and their current copies have been preserved. Keep `data/runs` untouched.
4. Tag the previous image IDs back to the tags recorded in `deployment.json` (older backups contain four images; new backups can contain six). Use the matching previous Compose source from Git in a separate clean recovery checkout, configured with the original absolute `PROJECT_DIR` and data mount. Do not discard a dirty checkout.
5. Run `docker compose up -d --no-build --wait --wait-timeout 150 reports runner` using the matching configuration. Check `/api/health`, the runner health status, retained reports, and the footer revision.

The initial migration also preserves a complete pre-Studio source and data archive outside the checkout. A crashed updater can leave `.maintenance`; use Start to retry Stop cleanup when its `action` is `stop`. For a failed Update guard, follow the image/database recovery steps before removing it. Verify its Portal job/container is no longer running and no other updater owns `.execution.lock` or `.lifecycle.lock` before manual intervention. Interrupted benchmark evidence from ordinary controller restarts remains visible; use Run again to create a fresh run.

## Restart behavior

An app-only restart preserves jobs and reconnects browser events. A controller restart reconciles surviving generation/verifier containers. It does not replay requests. Harbor's in-process trusted harness cannot survive controller termination; its trial artifacts are retained, its task containers are stopped, and the job is marked interrupted without a final score.
